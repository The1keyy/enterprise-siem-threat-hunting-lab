# SF-003 — Successful logon after failures

## Objective

Alert when Security 4624 succeeds for an account and source IP that just triggered SF-001. The technique on this alert is valid accounts (`T1078`) only. The guessing is SF-001.

## ATT&CK

`T1078` Valid Accounts. The fixture library maps it to Initial Access.

## Telemetry

Same Audit Logon success and failure as SF-001. The success event is 4624.

- Domain account success aimed at DC01 is collected on DC01.
- Local account success is collected on WS01.
- A domain account that logs on to WS01 produces the 4624 on WS01.

## Logic

Stock rule 60106 is level 3, "Windows Logon Success", and its event check includes 4624 and 4769. Nothing in `0580-win-security_rules.xml` requires earlier 4625s.

The sixth failure is alerted as 100100, so it is no longer 60122. Rule 100120 waits for that SF-001 alert, then a 4624:

- `if_sid` 60106 and `win.system.eventID` `^4624$` (drops 4769)
- `if_matched_sid` 100100
- `frequency="2"` and `timeframe="120"`
- `same_field` `targetUserName` and `same_field` `ipAddress`

`if_sid` plus `if_matched_sid` is the shape of built-in rule 2509. On sshd, `frequency="2"` fired when one prior burst alert was already in the window (SF-014). The same numbers are used here. Windows eventchannel was not replayed, so this copy is not a logtest result.

No rule in this image puts two `same_field` elements in one rule. Both are written. Whether analysisd requires the account and the source IP is not proven until the lab.

Level 12 is high (ADR 0004). A success after a burst is a session. It is not critical: a tired user can mistype and then succeed.

A 4624 after a same-IP spray that never reached six failures on that one account does not fire 100120. SF-003 follows SF-001, not SF-002. Step 14 can add the spray-then-success case once distinct users are counted.

## Exclusions

- `targetUserName` ending in `$` on the 4624.
- Nothing else. Logon type is not filtered. An interactive success and a network success both qualify if the account and source IP match the SF-001 alert.

## Validation procedure

Mac: `make logtest ID=SF-003` prints LIMITED.

Lab, Step 13, not run. **REQUIRES WINDOWS VALIDATION.**

1. Snapshot DC01 and WS01 first.
2. From `10.10.10.200` only, produce the SF-001 burst against domain account `sf-test-alice` on DC01, then one successful logon of that account from the same source.
3. Log off.

Cleanup: log off the session. Unlock and reset `sf-test-alice` if it locked. Do not leave the test logon active.

## Expected result

Rule 100120, level 12, description starting with `SF-003`, MITRE `T1078` only.

Five failures and then a success stay off 100120. A 4624 with no SF-001 alert stays on 60106 (or a more specific stock child).

## Observed result

`NOT YET VALIDATED`.

## False positives

Someone mistypes six times and then gets the password right. That is why this is high and not critical.

## Tuning

Widen `timeframe` only if a slow burst plus a success should still count. Do not fire on 60106 alone. Do not add `T1110.001` to this rule.

## Investigation

1. Confirm 100100 fired for the same account and source IP in the previous two minutes.
2. Record the account that succeeded and the logon type.
3. See whether the account is `sf-test-*` and whether you started the client at `10.10.10.200`.
4. If the source is unexpected, check the target host for a session and end it.

## Remediation

End the session, reset that `sf-test-*` password, and keep the source off the lab if it is not yours.

# SF-012 — WinRM / PowerShell remoting

## Objective

Alert when Sysmon records the WinRM host process, or a connection to the WinRM port. The technique is `T1021.006`.

## ATT&CK

`T1021.006` Windows Remote Management. Lateral Movement.

## Telemetry

Sysmon Operational event 1 and event 3 on WS01 and DC01.

Stock 92110, file `0810-sysmon_id_3.xml`, is `if_sid` 92101 or 61605, destination port `^5985$`, level 4, MITRE `T1021.006`. Rule 92220 matches `wsmprovhost.exe` on a Sysmon file-create, not on process creation. Process creation is 61603.

The ruleset channel list in `0575-win-base_rules.xml` has no `Microsoft-Windows-WinRM/Operational` rule. No built-in rule names a WinRM event ID. This detection does not invent one. Step 12 must add that channel on the agent. After a lab event shows the ID, a later rule can match it.

A 4624 type 3 is SF-011 rule 100512. It is not WinRM-specific, so it is not repeated here.

## Logic

The two rules do not wait for each other.

Rule 100520, level 12, is Sysmon 1 whose image ends in `\wsmprovhost.exe`. Level 12 is high (ADR 0004). A `wsmprovhost.exe` process means a remoting session started on the target. That is the named behavior, so the library row is high. It is not critical. Critical stays with SF-008.

Rule 100521, level 10, chains on 92110. Level 10 is medium and is above 92110, so a port-5985 connection is labeled SF-012. A port connection can be a scan. The process rule is the stronger alert.

Why path-based exclusions, not content: the command line of `wsmprovhost.exe` is attacker-influenced. The exclusion is the full agent executable path, which Sysmon records as the image or the parent image.

## Exclusions

- On 100520, `image` and `parentImage` must not be exactly `C:\Program Files (x86)\ossec-agent\wazuh-agent.exe`. The pattern accepts one or two backslash characters. VERIFY: that executable name is from 4.14.1 and 4.14.3 crash reports, not a checked 4.14.9 install. A custom install directory is not excluded. If the path does not match, the alert still fires.
- On 100521, the same image exclusion. `0810-sysmon_id_3.xml` has no `parentImage`, so this rule does not negate that field.
- `sourceIp` exactly `10.10.10.1` on 100521.
- Destination `127.0.0.1`, `::1`, or `-` on 100521. Local WinRM is not the lateral alert.

## Validation procedure

Mac: `make logtest ID=SF-012` prints LIMITED.

Lab, Step 13, not run. **REQUIRES WINDOWS VALIDATION.**

1. Snapshot WS01 and DC01 first.
2. On WS01, with WinRM already enabled on DC01, run `scripts/powershell/simulations/SF-012-WinRm.ps1`. The script does not call `Enable-PSRemoting`. `Invoke-Command` cannot bind. Expect source `10.10.10.20`.
3. Exit the session. Delete leftover `sf-test-*` accounts. Restore the snapshot if the host changed.

## Expected result

Rule 100520, level 12, for Sysmon 1 `wsmprovhost.exe`. Rule 100521, level 10, for destination port 5985. MITRE `T1021.006`.

`powershell.exe` does not fire 100520. The agent parent path does not. A loopback destination does not fire 100521.

## Observed result

`NOT YET VALIDATED`.

## False positives

An administrator runs a remoting session between lab VMs. That is a real `wsmprovhost.exe` and this rule is meant to show it.

## Tuning

Do not match the word WinRM in a script block. That text is SF-004's problem, not this one. When the WinRM Operational channel is collected, add a rule only for an event ID you have seen. Do not copy an ID from a blog into this file first.

## Investigation

1. Read `image`, `parentImage`, `sourceIp`, `destinationIp`, and `destinationPort`.
2. Confirm the computers are lab VMs and the account is `sf-test-*`.
3. Confirm you started the remoting session.
4. If the source is unexpected, keep the address and exit the session.

## Remediation

Exit the remoting session. Delete leftover `sf-test-*` accounts. Restore the snapshot if you are not sure what changed. This is a lab action, not an automated response.

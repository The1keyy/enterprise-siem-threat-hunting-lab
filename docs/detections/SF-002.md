# SF-002 — Password spray

## Objective

Alert when one source IP produces six Security 4625 failures inside 120 seconds. The roadmap name is password spraying (`T1110.003`). This rule does not count distinct usernames.

## ATT&CK

`T1110.003` Password Spraying. Credential Access.

## Telemetry

Same Audit Logon success and failure as SF-001.

- Domain account attempts aimed at DC01 are collected on DC01.
- Local account attempts are collected on WS01.
- Source address field: `win.eventdata.ipAddress`.

## Logic

`different_field` does not appear in the Wazuh 4.14.9 ruleset (zero matches under `/var/ossec/ruleset/rules`). A rule cannot say "many accounts, one IP" with a built-in option.

What is written instead is rule 100110: `if_matched_sid` 60122, `same_field` `win.eventdata.ipAddress`, `frequency="6"`, `timeframe="120"`, level 10. Six failures from one IP fire it whether the account names differ or not. Distinct-user counting is backend work in Step 14.

How this differs from stock 60204:

- Parent is 60122 (the fired 4625 id), not the whole `authentication_failed` group.
- Frequency 6 and timeframe 120, against stock 8 and 240, so a short lab burst shows up here first.
- MITRE is `T1110.003`, not `T1110`.
- Machine accounts and `ipAddress` `-` are excluded. 60204 excludes neither.

Level 10 is medium (ADR 0004). SF-001 is level 11. When one account reaches six failures from that IP, both rules match and 100100 wins, so the alert stays password guessing. A burst of six different accounts, one failure each, does not meet SF-001's same-account count, so 100110 is the rule that matches. That split is the shape of the rules. It is not proven until a Windows agent sends the events.

At eight failures, stock 60204 (also level 10) can match too. Which level-10 rule wins is not proven here. The lab procedure stops at six.

## Exclusions

- `targetUserName` ending in `$`.
- `ipAddress` exactly `-`. A dash means no source address, so it is not "one source IP". Local console failures often use `-`. Those can still be SF-001. They are not SF-002.
- Nothing else.

## Validation procedure

Mac: `make logtest ID=SF-002` prints LIMITED. The Mac check is a clean analysisd load.

Lab, Step 13, not run. **REQUIRES WINDOWS VALIDATION.**

1. Snapshot DC01 and WS01 first.
2. On WS01, run `scripts/powershell/simulations/SF-002-PasswordSpray.ps1`. The rule is six 4625s from one IP, not six accounts. The script fails twice each for `sf-test-alice`, `sf-test-bob`, and `sf-test-carol` so no single account reaches six (that would be 100100). Expect `ipAddress` `10.10.10.20`. Only four `sf-test-*` accounts exist.
3. Do not point this outside `sentinelforge.lab`.

Cleanup: stop the attempts. Unlock every `sf-test-*` account the lockout policy caught, and reset those passwords. On DC01 use `Search-ADAccount -LockedOut` and `Unlock-ADAccount`. If you tested a local account on WS01, unlock that local account too.

## Expected result

Rule 100110, level 10, description starting with `SF-002`, MITRE `T1110.003`.

Five failures from one IP do not fire it. Six failures with `ipAddress` `-` do not fire it. Six failures of one account fire 100100, not 100110.

## False positives

Many failed logons from one lab host, including a single account being guessed. Shared NAT would collapse people into one IP. This lab does not NAT the segment.

## Tuning

Do not treat 100110 as a finished spray detection. Step 14 has to count distinct `targetUserName` values before the severity should move. Until then, leave level 10.

## Investigation

1. List the account names in the six 4625s that share the source IP. If they are one name, this is SF-001's case and 100100 should be the alert.
2. Confirm the source is `10.10.10.200` and that you started it.
3. Check DC01 or WS01 for locked `sf-test-*` accounts.

## Remediation

Unlock and reset the `sf-test-*` accounts. If the source is not yours, keep it off the lab network.

# SF-014 — Linux SSH success after failures

## Objective

Alert when sshd accepts a login from a source IP that just triggered SF-013. The technique is valid accounts (`T1078`) only. The guessing itself is SF-013.

## ATT&CK

`T1078` Valid Accounts. Initial Access, as mapped in the fixture library.

## Telemetry

Same sshd syslog as SF-013, plus an `Accepted password` or `Accepted publickey` line (built-in rule 5715).

Logtest location: `/var/log/auth.log`. The Ubuntu 24.04 agent file or journal path is still **VERIFY**.

## Logic

Stock rule 5715 is level 3 and fires on any success. Nothing in `0095-sshd_rules.xml` requires earlier failures.

The 6th failure is alerted as 100701 or 100702, so it is not still rule 5710 or 5760. SF-014 waits for that SF-013 alert, then an authentication success from the same source IP inside 120 seconds:

- 100710 after 100701
- 100711 after 100702

`if_sid` plus `if_matched_sid` is the shape of built-in rule 2509. Logtest showed `frequency="2"` fires when one SF-013 alert is already in the window and the current event is 5715.

Level 12 is high (ADR 0004). A success after a burst is a session. It is not critical: a tired user can mistype and then succeed, and that should stay distinguishable from a level-15 event.

## Validation procedure

Mac:

```bash
make logtest-up
make logtest ID=SF-014
```

Lab, Step 13, not run:

1. Snapshot UBU01 first.
2. On WS01, run `scripts/powershell/simulations/SF-014-SshSuccess.ps1`. Six failures and the one success both use `ssh.exe` bound to `10.10.10.200` on WS01. That address is not a separate VM.
3. Log out.

Cleanup: stop the client, log out the session, and `faillock --user sf-test-alice --reset` if the account locked.

## Expected result

Rule 100710 or 100711, level 12, description starting with `SF-014`, MITRE `T1078` only.

Five failures and then a success stay on rule 5715.

## Observed result

`NOT YET VALIDATED`.

## False positives

Someone mistypes six times and then gets the password right. A shared admin workstation will attribute that to one IP. Both are real on a lab; they are why this is high and not critical.

## Tuning

Widen `timeframe` only if a slow typist plus a success should still count. Do not fire on 5715 alone.

## Investigation

1. Confirm SF-013 fired for the same source IP in the previous two minutes.
2. Record the account that succeeded.
3. See whether that account is `sf-test-*` and whether you started the client at `10.10.10.200`.
4. If the source is unexpected, check UBU01 for a new session (`who`) and end it.

## Remediation

End the session, rotate that account's password, and keep the source off the lab if it is not yours.

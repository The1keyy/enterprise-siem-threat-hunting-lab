# SF-001 — Repeated failed logons

## Objective

Alert when one target account produces six Security 4625 failures inside 120 seconds. This is password guessing (`T1110.001`).

## ATT&CK

`T1110.001` Password Guessing. Credential Access.

## Telemetry

Advanced Audit Policy subcategory **Logon**, Success and Failure. That policy writes 4624 and 4625. It is not the Account Logon subcategory. Account Logon is Kerberos and NTLM (4771, 4776). This image's `0580-win-security_rules.xml` has no 4771 or 4776 rule, and these detections do not use those events.

4624 and 4625 are written on the computer that handled the logon.

- Domain account logons aimed at DC01 are collected on DC01 (`10.10.10.10`).
- Local account logons are collected on WS01 (`10.10.10.20`).
- A domain account logon to WS01 is a WS01 event, not a DC01 4625.

Wazuh fields read from the 4.14.9 ruleset: `win.eventdata.targetUserName`, `win.eventdata.ipAddress`, `win.eventdata.logonType`, `win.eventdata.workstationName`. The parent that fires for 4625 is rule 60122.

## Logic

Chain in this image: 60000 → 60001 (Security) → 60104 (audit failure) → 60105 (event 4625) → 60122. Rule 60122 matches every 4625 because its event check is `^529$|^4625$`. Its text says "Unknown user or bad password". It does not filter on a status code. SF-001 inherits that.

Stock rule 60204 is "Multiple Windows Logon Failures": frequency 8, timeframe 240, `same_field` `win.eventdata.ipAddress`, group `authentication_failed`, MITRE `T1110`. It does not require one account. Rule 60203 uses `same_field` on `targetUserName`, but its parent is 60107 (privileged operation), not 4625.

SF-001 uses `frequency="6"` and `timeframe="120"` with `same_field` `win.eventdata.targetUserName` on 60122. Six is past a few typos and still shorter than the stock 8, so a lab burst is visible here before 60204. Level 11 is medium under ADR 0004. It is one above SF-002 and 60204 (both level 10) so a one-account burst stays `T1110.001` when the same-IP rule also matches.

## Exclusions

- `targetUserName` ending in `$` (machine account), `type="pcre2"` and `negate="yes"`. The default field matcher treats `$` as an end anchor, so the literal dollar is pcre2.
- Nothing else. SYSTEM, LOCAL SERVICE, NETWORK SERVICE, ANONYMOUS LOGON, logon type, and `127.0.0.1` are not excluded.

The `<field>` check sits on a frequency rule. No built-in rule in this image pairs those. Whether earlier machine-account 4625s inside the window still increment the counter is not proven here.

## Validation procedure

Mac: eventchannel is not replayed. `make logtest ID=SF-001` prints LIMITED. The Mac check is that analysisd loads the XML.

```bash
make logtest-up
docker exec wazuh-logtest grep -iE 'error|warning|sentinelforge' /var/ossec/logs/ossec.log | tail -n 30
```

Lab, Step 13, not run. **REQUIRES WINDOWS VALIDATION.**

1. Snapshot DC01 and WS01 first.
2. On WS01, run `scripts/powershell/simulations/SF-001-FailedLogon.ps1`. There is no `10.10.10.200` VM. `net use` cannot bind a source address, so the 4625 `ipAddress` is expected to be `10.10.10.20`. The script still adds `10.10.10.200` and the cleanup removes it. Stop at six failures for `sf-test-alice`. Do not point this outside `sentinelforge.lab`.
3. A local account uses the same rule on WS01. That path is the local-account case, not a second detection.

Cleanup: stop the attempts. If lockout policy locked the account, unlock it and reset the password on the `sf-test-*` account you used. On DC01 that is `Unlock-ADAccount`. On WS01, unlock the local account. Do not leave a session open.

## Expected result

Rule 100100, level 11, description starting with `SF-001`, MITRE `T1110.001`. Five failures stay on 60122. Six failures of `DC01$` do not fire 100100.

`NOT YET VALIDATED`. A clean rules load is not a lab run.

## False positives

A person mistypes one password six times. A scheduled task that retries one account does the same thing.

## Tuning

Raise `frequency` if lab users hit six typos often. Do not drop it to 1 or 2. Do not remove the machine-account exclusion.

## Investigation

1. Read `targetUserName`, `ipAddress`, `logonType`, and `workstationName` on the alert.
2. See whether SF-003 also fired (a success followed).
3. Check the source address in the event. The scripted SMB source is expected to be `10.10.10.20`. `10.10.10.200` is a secondary address on WS01, not a separate VM.
4. On the host in the event's computer name, open the Security log for that minute.

## Remediation

If the source is not yours, disable that `sf-test-*` account until you reset it, and keep the source off the lab. This is a lab action, not an automated response.

# SF-008 — User added to a privileged domain group

## Objective

Alert when Security 4728 or 4756 adds a member to Domain Admins, Enterprise Admins, Schema Admins, or Domain Controllers. The group is identified by the RID on `targetSid`, not by its display name. The technique is `T1098`.

## ATT&CK

`T1098` Account Manipulation. Persistence.

## Telemetry

Audit Security Group Management, Success, on DC01 (`10.10.10.10`).

- Domain Admins is a global group. Windows writes 4728. RID 512.
- Enterprise Admins and Schema Admins are universal groups. Windows writes 4756. RIDs 519 and 518.
- Domain Controllers is a global group. Windows writes 4728. RID 516.

VERIFY which of 4728 or 4756 DC01 actually emits. The rule accepts both. The planned simulation is on DC01 only.

Chain: 60000 → 60001 → 60103 → 60113 → 60141 (4728 or legacy 632) or 60151 (4756 or legacy 660). File `0580-win-security_rules.xml`. These rules add `^4728$|^4756$` and a `targetSid` check copied from the stock SID rules, which do not set `type="pcre2"`.

## Logic

One add is enough.

Rule 100310, level 15, matches RID 512 or 519. Level 15 is critical (ADR 0004). Stock 60159 (Domain Admins) and 60167 (Enterprise Admins) are level 12, cover add and remove, and use MITRE `T1484`. Adding a member to either group is domain or forest admin, so this rule is critical and one step above those stock rules. An add is labeled SF-008. A removal stays on the stock rule.

Rule 100311, level 13, matches RID 518 or 516. Level 13 is high. Stock 60166 and 60164 score those changes at 12 and also match removals. The library row is critical because 100310 is the Domain Admins and Enterprise Admins behavior.

Local Administrators (`S-1-5-32-544`, event 4732) is SF-007, not this rule.

The match is the SID. A 4728 whose `targetUserName` says Domain Admins and whose `targetSid` ends in `-513` does not fire.

Exclusions use anchored SIDs, not a group name. This rule has no exclusion: every add to these RIDs is the behavior.

## Exclusions

None.

## Validation procedure

Mac: `make logtest ID=SF-008` prints LIMITED.

Lab simulation not run. **REQUIRES WINDOWS VALIDATION.**

1. Snapshot DC01 first.
2. On DC01 only, inside `sentinelforge.lab`, run `scripts/powershell/simulations/SF-008-DomainAdmins.ps1` with `-IUnderstandDomainAdmins` and type `I will remove sf-test-carol`. It adds `sf-test-carol` to Domain Admins. It does not download an Atomic test.
3. Immediately run `SF-008-DomainAdmins-Cleanup.ps1`. Do not leave `sf-test-carol` in Domain Admins. Restore the snapshot if the host changed.

## Expected result

Rule 100310, level 15, or rule 100311, level 13. Description starts with `SF-008`. MITRE `T1098`.

A 4728 for Domain Users (RID 513) does not fire 100310. A 4729 removal from Domain Admins does not. A display name of Domain Admins with RID 513 does not.

## Observed result

`NOT YET VALIDATED`.

## False positives

A domain administrator adds a lab account to Domain Admins, Enterprise Admins, Schema Admins, or Domain Controllers during a test.

## Tuning

Do not match the group name. Do not add the removal events 4729 or 4757. If a lab group other than these four RIDs should alert, add that RID as its own anchored `targetSid` check.

## Investigation

1. Read `targetSid`, `memberSid`, `memberName`, and `subjectUserName`.
2. Confirm the computer is DC01 and that the RID is 512, 519, 518, or 516.
3. Confirm the account is `sf-test-*` and that you started the Atomic test.
4. If the member is unexpected, keep the SID and remove the membership.

## Remediation

Remove the member from that group. Delete leftover `sf-test-*` accounts. Restore the snapshot if you are not sure what changed. This is a lab action, not an automated response.

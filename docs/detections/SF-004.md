# SF-004 — Suspicious PowerShell script block

## Objective

Alert when PowerShell Script Block Logging records a 4104 event whose text contains a high-signal execution string. The technique is `T1059.001`.

## ATT&CK

`T1059.001` PowerShell. Execution.

## Telemetry

PowerShell Script Block Logging, event 4104, channel `Microsoft-Windows-PowerShell/Operational`.

Turn that logging on before expecting an event. The planned simulation runs on WS01 only. The rule itself matches any agent that sends 4104.

Parent in this image: 60000 → 91801 (that channel) → 91802 (`ScriptBlockId` is present). File `0915-win-powershell_rules.xml`. That file never checks event ID 4104. Rule 100200 adds `^4104$`.

Field used: `win.eventdata.scriptBlockText`. Matching is `(?i)` pcre2, which that file already uses (42 times).

## Logic

One event is enough. This is not a frequency rule. The string is the signal.

The pattern is `IEX` as a whole word, `Invoke-Expression`, `FromBase64String`, `Invoke-Mimikatz`, `AmsiUtils`, `amsiInitFailed`, `AmsiScanBuffer`, or `-nop` / `-NoProfile` followed by `-w hidden` or `-windowstyle hidden`.

Stock rule 91837 is level 4 and matches `IEX` or the misspelled `Invoke-Expresion`, plus `Get-Content -Stream`. It does not match the spelled-out `Invoke-Expression`. Stock rule 91809 is level 10, MITRE `T1140`, and matches only `FromBase64String`. Level 12 is high (ADR 0004). It is above both of those, so a block that also matches them is labeled SF-004.

## Boundary with SF-006

100200 does not look for `Net.WebClient`, `DownloadString`, `DownloadFile`, `Invoke-WebRequest`, or `Start-BitsTransfer`. A script block that only contains those strings does not fire SF-004. A block that contains `Invoke-Expression` and `DownloadString` can fire both. The cradle half is SF-006.

## Exclusions

- `scriptBlockText` containing `ossec-agent` or `sentinelforge-setup`.
- Nothing else.

The 4.14.9 PowerShell rules never reference a script `Path` field, so this exclusion is text inside `scriptBlockText`. Lab setup scripts must include the marker `sentinelforge-setup`. A Wazuh agent script is excluded when its logged text contains `ossec-agent`.

## Validation procedure

Mac: `make logtest ID=SF-004` prints LIMITED.

Lab, Step 13, not run. **REQUIRES WINDOWS VALIDATION.**

1. Snapshot WS01 first.
2. On WS01 only, with Script Block Logging already on, run an Atomic Red Team test for `T1059.001`. Do not point it outside `sentinelforge.lab`.
3. Run the cleanup that belongs to the Atomic test you ran. End any leftover `powershell.exe` or `pwsh.exe`. Restore the snapshot if the host changed.

## Expected result

Rule 100200, level 12, description starting with `SF-004`, MITRE `T1059.001`.

A block that only says `DownloadString` does not fire 100200. `Write-Output hello` does not. Text that also contains `sentinelforge-setup` does not.

## False positives

An administrator script calls `Invoke-Expression` or decodes a string with `FromBase64String`. Bare `IEX` is common enough that stock Wazuh scores it level 4. This rule scores the whole set at 12 because Mimikatz and the AMSI strings are in the same rule.

## Tuning

Split `IEX` and `FromBase64String` onto a lower level if WS01 admin scripts trip 100200. Do not add the SF-006 cradle strings to this rule.

## Investigation

1. Read the script block text on the alert. Confirm which string matched.
2. See whether SF-006 also fired for the same host and minute.
3. Confirm the computer is WS01 and that you started the Atomic test.
4. If the source is unexpected, keep the script text and look for a new process from that second.

## Remediation

End the PowerShell process on WS01 if it is still running. Restore the snapshot if you are not sure what the test changed. This is a lab action, not an automated response.
